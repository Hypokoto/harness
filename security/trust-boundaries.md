# Trust Boundaries

The Harness Runtime is designed around strict demarcation points between untrusted data streams and the trusted execution engine.

## 1. The MCP Adapter Boundary (`McpTool`)
- **Untrusted:** Standard IO streams, JSON-RPC payloads, server errors, result content structures.
- **Enforcement Point:** Schema parsing, depth verification (max 20 levels), byte limits (max 5 MB).
- **Trusted:** Internal `Tool` interface structures provided to the `ToolRegistry` and `AgentLoop`. 

## 2. The Context & Discovery Boundary (`ToolIndex`)
- **Untrusted:** Plugin manifest descriptors, server name declarations, advertised capabilities.
- **Enforcement Point:** strict binary equivalence checking, identity registration uniqueness, tool duplication blocks, capability validation (`parseCapability`).
- **Trusted:** Resolved routing structures linking logical tools to their underlying transport plugins.

## 3. The Execution Authorization Boundary (`ToolRegistry.execute()`)
- **Untrusted:** Invocation intent initiated by the Model or Agent Loop (via execution payloads).
- **Enforcement Point:** Active `PermissionDecision` logic intersecting `requiredCapabilities` against `grantedCapabilities`, bounded by TOCTOU verifications upon async yields.
- **Trusted:** Authorized operations actively dispatched to the local/remote execution queues.

## 4. The Data/Event Encapsulation Boundary (`AgentLoop` / `EventStore`)
- **Untrusted:** Result payloads generated by executed external tools.
- **Enforcement Point:** Forged top-level events (e.g. `type: 'permission.allowed'`) returned by tools are strictly wrapped within the `.result` property of legitimate `.tool_completed` events, neutering their potential authoritative execution status during replay.
- **Trusted:** The monotonically incrementing internal ledger representing exact machine state.
